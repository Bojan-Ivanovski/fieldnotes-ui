# Adopting fieldnotes-ui in consumer applications

Fieldnotes app migration is not planned. The historical source mappings below illustrate how a consumer can adopt the library incrementally; they do not schedule changes to that application.

The original Fieldnotes application was audited at HEAD 218bcc0 plus its existing uncommitted hosted/discovery work. It remains unchanged. The library is independent and package consumers were tested before recommending replacements. Do not delete old implementations until the corresponding application flow passes its own regression tests.

1. After an authorized release, install the final verified package version. Before publication, install the reviewed npm tarball. Never import sibling source or reverse the dependency direction.
2. Import `fieldnotes-ui/styles.css` once in the application entry/global layout. Wrap the application in `<ThemeProvider defaultTheme="fieldnotes-dark">` to retain the POC identity. The companion light theme is new. Preserve Manrope loading and its OFL notice in the app; the library ships no font binary.
3. Replace duplicate actions first, then forms/cards/search, then dialogs and navigation. Keep the application functional at every step. Explicitly use `type="submit"` where a former native button submitted a form; library Button defaults to button.
4. Run application tests for saving, recovery, imports, permissions, account flows and routing after each replacement. Consumer checks prove the package contract, not these domain workflows.
5. Remove only the duplicate CSS that has verified replacements. Retain app layout, prose, CodeMirror, review-note and discovery-page styles until separately migrated. Prefix collisions are avoided by fn- classes; old global selectors may still affect native elements, so remove/contain those deliberately.

Full MarkdownEditor, DocumentPane, source-fidelity projection, annotations, saves, recovery, authentication, settings, permissions, importing, backend APIs and complete discovery pages intentionally remain application implementations. An optional editor adapter, prose stylesheet, rich resource loading/virtualization and further patterns are future work with separate contracts; none is included as a stub.

Compatibility: initial tested React range starts at 19.3.1; tooling Node 24+. React 18 is not claimed. Next.js App Router consumers render client boundaries from server pages; hooks and theme factories run in client modules. Supply the same initial theme server/client to avoid mismatch; cookie-based initial preferences avoid localStorage hydration flashes. Scoped portals should have unclipped ancestors. Custom CSS tokens need a contrast review.
