# 0.4.0: application patterns and advanced components

This plan defines the work after [0.3.0](0.3.0.md); it does not claim either milestone has shipped. Build on the accepted 0.3.0 card, search, navigation and ResourceExplorer contracts rather than duplicating them. Component names and exact prop shapes remain subject to implementation review. This planning change does not change the package version.

## Source evidence and boundaries

The paths below refer to the sibling Fieldnotes application. Use them as extraction evidence, not as instructions to migrate or copy the full application.

| Source evidence                                                                                                                                 | Responsibility to extract                                                        | Responsibility retained by the consumer                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `src/components/DocumentPane.tsx`: document toolbar, breadcrumbs, title, actions and save indicator                                             | Document workspace composition and visible operation status                      | Document model, permissions, navigation guards, persistence and recovery         |
| `DocumentPane.tsx`: Write/Split/Read controls, source and preview panes; `src/styles.css`: responsive split stacking                            | Editor chrome and responsive pane layout                                         | Editor engine, Markdown parsing/sanitization, content, undo history and commands |
| `DocumentPane.tsx`: outline/review rail, heading, close and toggle controls; CSS turns the rail into a fixed panel on narrow screens            | Accessible supporting panel and focus transitions                                | Outline generation, annotation anchors, notes, scrolling to document content     |
| `src/features/hosted/WorkspaceSettings.tsx` and `ProjectSettings.tsx`: section switching, forms, pending/error feedback and destructive actions | Settings layout and composed examples                                            | Membership, roles, authorization, mutations and domain validation                |
| Existing ResourceExplorer renders loaded visible rows without windowing; source resource collections are paginated                              | Measured large-collection behavior and an evidence-based virtualization decision | Fetching, cursors, filtering policy and resource identity                        |

The source demonstrates split layouts, not pointer-resizable panes or drag-and-drop. Those require the prototypes and explicit decisions below before any public API commitment. No mandatory editor dependency, global shortcut manager, router, backend client, storage adapter or permission system belongs in these patterns. Native editor/preview content stays in consumer-provided slots; the library does not render arbitrary Markdown or HTML.

Fieldnotes app migration has been removed from the roadmap. 0.5.0 focuses on component refinement and API stabilization. Do not edit the app as part of this milestone. Reuse existing lower-level components and semantic tokens; introduce reusable patterns only where composition needs a shared contract, and document recipes where existing primitives suffice.

## Work packages and acceptance criteria

### 1. [Document workspace and operation status](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/28)

Compose a page header with breadcrumb, title, metadata and actions, followed by main content and an optional supporting panel. Work inside ApplicationShell without adding a second main landmark. Keep consumer heading levels, native attributes, refs and action handlers intact. Long titles and numerous actions must wrap or use an explicit overflow menu without hiding required functionality.

Demonstrate saved, saving, unsaved and failed states using consumer-supplied status and messages. Do not invent an autosave engine, persistence callback or generic recovery protocol. Use visible text as well as color; announce meaningful transitions politely without repeating on every keystroke or rerender. A persistent failure message and retry/download actions compose from existing feedback/actions, with execution owned by the example consumer.

Acceptance: document workspace examples cover editable and read-only content, missing metadata, long names, pending and failed operations, and action overflow. Status-only updates never move focus. Header actions remain keyboard reachable at narrow widths and increased text size. The composition preserves native semantics and does not require a Fieldnotes document type.

### 2. [Responsive editor layout and toolbar composition](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/29)

Provide layout for consumer-supplied editor, preview and secondary actions, supporting write, read and split modes plus a distraction-reduced focus mode. Mode and focus state support stable controlled/uncontrolled ownership. Define mode selection with existing Tabs where its tab/panel model fits; use correctly named groups for ordinary actions. Only use toolbar semantics if the corresponding keyboard model is implemented. Do not register application-wide shortcuts.

Split mode shows both panes on wide screens and stacks them on narrow screens. Changing a breakpoint changes layout without destroying editor state. Define mount/preservation behavior for explicit mode changes; provide an example proving that switching away and back preserves consumer text and selection through the documented contract. Hidden panes cannot retain keyboard focus. If a mode change hides the active pane, focus moves to the mode control that initiated it, without overriding a consumer's explicit focus handling. Preference persistence is consumer-owned.

Acceptance: keyboard mode switching, visible focus, disabled commands and active control semantics work; responsive transitions preserve content and avoid duplicate editor instances/IDs. Focus mode exposes an obvious exit control. The example uses a lightweight controlled editor stand-in, proves content continuity, and does not import an editor engine into the package or minimal Button consumer. Editing, parsing, export, undo and save behavior remain consumer callbacks/content.

### 3. [Supporting details panel](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/30)

Compose a named desktop aside with heading, close action, content and optional footer. On narrow viewports use the existing maintained Dialog primitive for a modal drawer, including scoped portals, focus trap, Escape, outside dismissal and scroll handling. Outline and notes are examples of consumer content, not new domain models. Reuse the 0.3.0 mobile state ownership conventions.

Define one open-state contract with controlled/uncontrolled support. Mount only one copy of the panel content at a time. Document whether a desktop/mobile presentation transition remounts content; keep durable content state in the consumer. Closing returns focus to the invoking control, with a documented fallback if it was removed. Across a breakpoint, transfer focus only if it was in the affected panel; opening a desktop aside must not steal focus from the editor. Modal transitions must satisfy the drawer's focus containment requirements. Coordinate with ApplicationShell so Escape closes only the topmost modal and competing drawers do not create two active focus traps.

Acceptance: outline/notes switching, close/reopen, focus-mode hide/restore, desktop/mobile transitions and removed triggers are covered by actual activeElement assertions. Mobile content remains scrollable and reachable without page overflow; labels and IDs remain unique. Consumer state survives documented remounts. Test the details drawer together with mobile navigation and open nested overlays.

### 4. [Settings layouts and composed forms](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/31)

Provide a settings page/section recipe or minimal reusable layout with title, description, section navigation, fields, feedback, submit actions and a distinct destructive-action section. Reuse existing Tabs, Fieldset, ErrorSummary, Dialog and ConfirmDialog rather than adding form-state management. Document when sections are local tabs and when they are destination links. A modal settings example uses one form per submission boundary with no nested forms.

Acceptance: examples demonstrate dirty edits, pending submission, success, field errors, submission failure/retry and a destructive confirmation. The consumer decides whether a pending operation blocks dismissal or navigation; demonstrate a guard that rejects leaving without losing entered values. Error-summary links focus the invalid native controls. Required/disabled semantics and native submission remain intact, and focus returns after confirmation or cancellation. No workspace role, account API or validation library becomes a package dependency.

### 5. [Large-collection measurements and virtualization decision](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/32)

Build reproducible, deterministic fixtures for 1,000 and 10,000 loaded records with flat and nested shapes, partial expansion and fully expanded stress cases. Measure the 0.3.0 implementation before optimizing. Record the browser/build, hardware, viewport, CPU throttling, visible/loaded row counts and at least five runs; report median and p95 for initial render, filtering and keyboard focus movement, plus DOM row count and long tasks. Use a production packed consumer; collect timings without screenshot or accessibility-audit overhead. Include the fixture seed, scripts and trace/artifact locations so another contributor can reproduce the report.

Before comparing implementations, record the representative supported workload and interaction budgets in the report. Distinguish that release gate from the 10,000-row stress case; do not relabel a failing representative case as stress after measuring. Compare pagination, constrained expansion and rendering changes before introducing virtualization. The required deliverable is a measured decision: implement virtualization if the representative workload misses the recorded budgets and windowing resolves it; otherwise document the supported envelope and retain the simpler renderer. Any unresolved representative-workload regression blocks completion of this issue.

If virtualization is warranted, evaluate maintained primitives and keep optional heavy runtime out of basic imports. Acceptance includes offscreen keyboard navigation, scroll-to-focused-item, stable IDs/selection, accurate tree position metadata, filter/update focus recovery, branch loading/retry/pagination and a documented accessibility tradeoff assessment. A visual speed improvement alone does not establish accessibility. If those contracts cannot be met, revise the rendering design or explicitly revise milestone scope before claiming the work complete. Do not silently raise existing package budgets.

### 6. [Resizing and drag-and-drop prototypes](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/33)

Investigate these as separate interaction designs; they are not promised public components. Produce a small reviewable prototype and decision record for each, identifying a concrete workflow, benefits, alternatives, dependency/license/bundle cost and accessibility limitations. A decision may retain an example-only prototype or defer a public API with reasons; the investigation itself is mandatory.

For resizing, prototype a labelled keyboard-operable separator with arrow increments, minimum/maximum bounds, reset, pointer/touch interaction and stable behavior at responsive transitions. Verify resizing does not capture editor shortcuts or produce unusable collapsed panes. Sizing persistence stays consumer-owned.

For resource movement, prototype pointer and keyboard initiation, valid/invalid targets, cancellation, focus restoration and announced outcomes. Supply an equivalent move action/dialog usable without dragging. Permission checks, cycle prevention, asynchronous acceptance/failure and persistence belong to the example consumer; a rejected move must leave the collection unchanged. Coordinate with tree pagination/filtering and avoid implying unloaded destinations are validated.

Acceptance: commit both prototype outcomes and link the supporting interaction evidence. Adopt a public API only through an explicitly reviewed follow-up implementation issue with full docs, tests and Changeset; if adopted for 0.4.0, that issue becomes a release prerequisite. Neither prototype adds a mandatory package dependency or unsupported feature claim by itself.

### 7. [Integrated examples, compatibility and release validation](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/34)

Ship a document-workspace example combining ApplicationShell, 0.3.0 navigation/search/tree, workspace chrome, supplied editor/preview and supporting panel. Include delayed/failed save feedback and outline/notes switching. Ship a settings example with section navigation, native forms, error summary and destructive confirmation. Keep prior milestone examples available. Mock behavior must be deterministic and clearly distinguish consumer responsibilities from package behavior.

Acceptance: public APIs have defaults, state ownership, semantics, refs, mount behavior, accessibility and limitations documented, with interactive stories. Validate all seven presets, keyboard-only operation, focus transitions, 320px mobile layouts, 200% zoom, reduced motion, forced colors and themed portals. Run automated accessibility checks and inspect intentional screenshot changes in the pinned browser environment. Document manual assistive-technology checks that remain unperformed; production validation stays an explicit 0.5.0/1.0.0 gate.

Run format, lint, typecheck, architecture, meaningful component tests, build, exact export/package verification and licenses, then Storybook, real packed Vite/Next consumers and browser/visual checks. Confirm the minimal Button consumer excludes editor, tree, overlays and any optional advanced runtime. Preserve current limits of 25,000 bytes distributed CSS, 300,000 bytes unpacked package and 300,000 bytes minimal-consumer raw JavaScript; investigate growth and require an explicit reviewed budget change rather than quietly relaxing a verifier. Public changes receive appropriate minor Changesets. Passing CI must cover the final implementation commit.

## Dependencies and release gates

0.3.0 is still implementation work, not an already released dependency. Reconcile these plans against its final APIs before starting public 0.4.0 component work. Within 0.4.0, start with workspace structure, then the supporting panel and editor chrome, then settings composition. Begin performance measurement and the advanced prototypes early so their findings can inform the layout/tree design. Integrated examples depend on the completed component work and recorded performance/prototype decisions.

The [0.4.0 milestone](https://github.com/Bojan-Ivanovski/fieldnotes-ui/milestone/4) tracks these seven work packages. Each gets a reviewable PR with acceptance evidence. A conditional advanced feature needs a linked implementation issue if adopted; a documented deferral does not remove any of the mandatory layouts, examples, measurements or prototypes above. There is no promised release date before those dependencies and decisions are resolved.

Keep the milestone open after implementation issues close. Prepare the version/changelog and review compatibility changes when implementation is ready. Publish the GitHub release only when requested, against a verified commit with its tested tarball, then close the milestone. npm publication remains separately locked until account setup is complete.
