# 0.3.0: composites, search, tree views and navigation

This is an implementation plan, not a claim that these capabilities have shipped. The package remains at 0.2.0 until the release preparation step. Existing SearchField, ResourceExplorer and ApplicationShell APIs are the starting point. Prefer additive composition and preserve their existing behavior; document any necessary breaking change before implementation.

## Source evidence and boundaries

The source paths below refer to the sibling Fieldnotes application audited for this plan. They are evidence for extraction, not files to migrate in this milestone.

| Application evidence                                                                                                                                   | Existing library gap                                                     | Planned responsibility                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `src/features/discovery/PublicHome.tsx`: submitted search, counts, result links/cards, error retry and paginated results                               | SearchField only renders the input, clear action and spinner             | Compose search and result states around ordinary document links and cards                   |
| `src/App.tsx`: document cards with open, favorite, management and trash actions; `PublicHome.tsx`: workspace title anchors and sibling account actions | No reusable resource card composition                                    | Native article, title, description, metadata and sibling actions without app data contracts |
| `src/App.tsx`: counted navigation and actions gated by an asynchronous editor flush                                                                    | Sidebar is a layout slot; mobile drawer state is internal                | Semantic navigation composition and consumer-controlled drawer state                        |
| `src/features/hosted/ResourceTree.tsx`: per-branch pending/error/retry, empty children and load more                                                   | ResourceExplorer assumes a fully available synchronous nested collection | Consumer-supplied branch states and actions with a defined keyboard model                   |
| `src/App.tsx`: local document filtering; ResourceExplorer currently rebuilds on item changes                                                           | No ancestor-preserving tree filter or verified DOM focus recovery        | Filter loaded tree data and preserve usable focus through updates                           |

Queries, debounce, request cancellation, stale-response protection, cursors, routing, permissions, selection business rules and optimistic mutations stay consumer-owned. The examples must demonstrate this ownership, including a stale response that must not replace newer results. Tree filtering searches loaded data only; remote search is explicitly a consumer operation.

Do not introduce a combobox or listbox for document results: these are navigable collections, with native Tab/Enter behavior. A future command palette needs separate evidence and interaction design. Virtualization, drag-and-drop, editor layouts and production app migration remain in later milestones.

## Work packages and acceptance criteria

### 1. [Resource card composition](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/22)

Use native article content and reuse existing surface, typography and action controls. Support a primary native anchor or button, description, metadata and separate actions. Keep titles and accessible names consumer-owned; do not require Fieldnotes resource types, routing or date formatting. Prefer children and a small number of slots over a large card data schema.

Acceptance: link and button examples work with keyboard activation; favorite/menu/restore actions never trigger the primary action; no nested interactive elements or whole-card click handler; native props and refs reach their documented elements. Long titles, missing metadata, disabled/busy actions, narrow viewports and all built-in themes remain readable.

### 2. [Search and result composition](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/23)

Reuse SearchField. Define the minimum shared result-region/status composition from both local live filtering and submitted search. Keep draft input separate from submitted query in the submitted example. Use native list or grid content with an accessible heading/name, rather than taking ownership of result rendering or selection.

Acceptance: initial, loading, successful empty, populated, failed and retry states have distinct examples; count/status announcements are polite and do not repeat on every render; stale results versus initial loading are documented. Pagination preserves existing results and focus on the load-more action; duplicate requests are prevented while pending; an append failure permits retry. Clearing the search returns focus to the input. A consumer-side out-of-order response example proves newer results win.

### 3. [Navigation and mobile drawer control](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/24)

Compose a named navigation landmark, groups and items with labels, optional decorative icons and counts. Destination links retain href and browser behavior; callback actions remain buttons. Specify current-page versus action state semantics without treating every item as a toggle. Group heading actions remain separate from destination controls.

Add controlled and uncontrolled mobile navigation state to ApplicationShell, following the library's stable state-ownership convention. The consumer closes the drawer after an accepted navigation; a rejected or pending save guard leaves it open. Do not close automatically on arbitrary child clicks.

Acceptance: native link modifiers and button activation work; active destination semantics are exposed; counts do not obscure names. Cover trigger, Escape, outside dismissal, focus return and desktop/mobile transitions, including consumer-controlled state, a rejected navigation and no duplicate sidebar landmark. Document the controlled breakpoint behavior and SSR/hydration constraints before finalizing the props.

### 4. [Resource explorer filtering, branch states and focus](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/25)

Keep stable resource IDs, consumer-owned selection/expansion and the maintained tree primitive. Specify filter behavior before coding: include matching loaded items and their ancestors, expose matching descendants, preserve stored expansion when filtering ends, and define whether a matching folder includes nonmatching descendants. Use a consumer predicate or equivalent composition without assuming backend search semantics.

Represent unloaded folders independently from files and loaded empty folders. Define pending, failed/retry and partially loaded/load-more branch states without embedding fetch logic. Expanding an unloaded branch must expose a consumer notification; repeated activation while pending must not duplicate a request. Successful loads retain expansion; errors retain loaded siblings; retry and append actions identify their branch.

The first implementation step is a keyboard/semantic prototype using the existing tree primitive. Compare branch actions outside the tree with actions integrated through supported tree behavior, and record the chosen model. Ordinary nested buttons inside a roving-focus treeitem are not an acceptable shortcut. Do not freeze a public branch-state API until the prototype demonstrates reachable actions, coherent arrow navigation and meaningful accessible names. This is an implementation gate, not deferred scope.

Acceptance: keyboard expansion, collapse, Home/End, typeahead and activation continue to work; loading, retry and pagination are reachable without pointer use. Filter changes, branch collapse, removal of the focused item, appended data and an empty collection have deterministic focus behavior. Restore DOM focus only when focus was already inside the explorer; never steal it from search or another control. Document fallback priority and test actual activeElement, not only the tree's internal focused ID. Filtering does not emit spurious user selection or expansion callbacks. Define disabled-item behavior and cover it in these transitions.

### 5. [Integrated example and release validation](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/26)

Build a searchable library example combining cards, navigation, tree and ApplicationShell, using deterministic mock data and simulated delayed/failing requests. Show local filtering, submitted search, branch retry/pagination and accepted/rejected mobile navigation. Keep the existing 0.2.0 example available.

Acceptance: document every public API's defaults, state ownership, refs, semantics and limitations; add interactive stories and meaningful component/browser tests for the contracts above. Verify all seven presets, keyboard focus, mobile overflow, forced colors and automated accessibility, and inspect intentional screenshot changes in the pinned browser environment. Verify typed root/layer exports and real packed Vite/Next consumers. Keep minimal-consumer isolation and existing artifact/CSS size budgets; investigate growth rather than silently raising limits.

Run formatting, lint, typecheck, architecture, component tests, build, package verification and licenses, then Storybook, packed consumers and relevant browser/visual checks. Passing CI must cover the final implementation commit. Public changes receive minor Changesets; planning alone does not require one. Manual assistive-technology validation remains an explicit production gate for 0.5.0/1.0.0, with its unperformed status documented.

## Order and release gates

Start with cards and navigation; search composition then has real result content. Prototype the asynchronous tree model early, before settling its public API, and implement filtering/focus recovery with that model. Complete integration and package/browser validation after the component families are available. Each family gets a reviewable PR with its relevant acceptance evidence; the integrated example validates their combined behavior.

The [0.3.0 milestone](https://github.com/Bojan-Ivanovski/fieldnotes-ui/milestone/3) tracks these five work packages. Their acceptance criteria are implementation deliverables, not proposals for optional follow-up. Issue completion does not close the milestone. Release preparation reviews the changelog and compatibility impact, applies the version update, and verifies the final tarball. Publish a GitHub release only when requested, against a verified commit with the tested asset, then close the milestone. npm publication remains separately locked until account setup is complete.
