## 0.2.0 acceptance criteria

The 0.1.0 inventory deliberately deferred breadcrumb and toast APIs and contained only basic native forms and action menus. This milestone completes those gaps and adds supporting core form/overlay building blocks. It does not pull application workflows or form state management into the package.

- **Forms ([#11](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/11)):** Label, Fieldset with legend/description/error and native disabled propagation, ErrorSummary with links that focus invalid controls, native Switch submission/reset/controlled behavior, and Checkbox mixed state with refs. Existing native validation and Field contracts stay compatible.
- **Navigation ([#12](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/12)):** Breadcrumb composition and current-page semantics; semantic/decorative horizontal/vertical Separator; dropdown groups/labels, checkbox and radio choices, keyboard submenus with disabled items and scoped portals. Routing remains consumer-owned.
- **Overlays ([#13](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/13)):** Radix Tooltip focus/hover and Escape behavior, interactive Popover focus/close/outside dismissal and controlled state, and Toast composition with actions/close, queue examples, duration/hover pause, F8 viewport access and swipe dismissal. Nearest theme scope and viewport bounds are preserved.
- **Validation ([#14](https://github.com/Bojan-Ivanovski/fieldnotes-ui/issues/14)):** Typed public exports and real tarball consumers; meaningful component tests; interactive stories; browser keyboard/focus/error tests; axe across seven presets with open overlays; mobile/forced-colors checks; existing visual regressions; passing format/lint/types/architecture/build/licenses and GitHub CI. Document APIs, defaults, accessibility and limitations. A minor Changeset prepares 0.2.0.

Manual screen-reader checks remain explicit production gates for 0.5.0/1.0.0. Automated browser checks are not a claim of full WCAG certification. Virtualization, drag-and-drop, editors, data fetching, authentication and production integration are outside this milestone.

## Release lifecycle

Track work in the version's GitHub milestone and merge through passing CI. Completing issues does not close the milestone. Prepare/review the version and changelog when ready to release. Create the GitHub release against the verified commit and attach the tested tarball; only then close its milestone. `release-milestone.yml` closes matching milestones for published GitHub releases, and the npm release workflow explicitly closes them as well because GitHub-token-created releases do not trigger other workflows. Publishing a tag alone or merging implementation work does not close a milestone. Do not run npm publishing while it is locked.
